Act 10: What SOLA Is Good For

Strengths, limitations, and the honest grammar of SOLA's outputs.

Part of My Take on SOLA.

After Three Pillars

We have now examined all three pillars on which the case for SOLA rests.

The first pillar was no prior information. Act 7 showed that without model-side assumptions, the gap between the resolved property \(\mathcal{A}(\bar m)\) and the true target property \(\Tau(\bar m)\) is unbounded. A good-looking resolving-kernel plot does not, by itself, close that gap. The boundary is real, and it is the same boundary that classical inversion has long since accepted.

The second pillar was resolution control. Act 8 showed that SOLA's resolving kernels are target kernels passed through the adjoint of a resolution operator: \(R_k = \mathcal R^*T_k.\) This is useful — it gives visibility and design control — but it is not a new species of resolution. The resolution operator has not been bypassed. It has been moved to a different place in the formula.

The third pillar was uncertainty quantification. Act 9 showed that SOLA's default uncertainty — the shifted-noise pushforward \(\mathcal{N}(\mathbf X\widetilde{\mathbf d},\mathbf X\mathbf C_D\mathbf X^*)\) — is not a posterior. It is a data-space jitter centred on the observation. Without a prior, the observed data cannot be turned into a probabilistic statement (conditioned on the observed data) about the approximate property of the true model. The frequentist interpretation — pushing the noise through \(\mathbf X\) and building calibrated confidence sets — gives a clean framework that does not require a prior, but it produces coverage statements, not posterior beliefs.

Checkpoint

All three pillars share the same boundary: without model-side information, SOLA can report resolved properties and their resolving kernels, but it cannot cross from there to exact target properties or posterior beliefs.

So where does that leave SOLA? In a perfectly good place — provided we read its outputs with the right grammar.

What SOLA Does Well

SOLA is excellent at constructing controlled linear combinations of data. Given data \(\widetilde{\mathbf d}\in\D,\) it builds a finite-dimensional map \(\mathbf X:\D\to\Pspace\) and reports \(\widetilde{\mathbf p} = \mathbf X\widetilde{\mathbf d}.\) Because the map is linear, the output is easy to compute, easy to inspect, and easy to propagate data noise through.

Although the resolving kernels are simply target kernels filtered through a resolution operator that is not fundamentally different from what normal linear inversions produce, they still provide a more principled analysis of targeted properties.

For each property component, \([\widetilde{\mathbf p}]_k = \sum_{i=1}^{N_d}[\mathbf X]_{ki}[\widetilde{\mathbf d}]_i,\) and, in the noiseless idealization, \([\widetilde{\mathbf p}]_k = (R_k,\bar m)_{\M},\) where \(R_k = \sum_{i=1}^{N_d}[\mathbf X]_{ki}K_i.\) Thus the method tells us not only the number it reports, but also the linear functional of the model that produced that number.

Lesson

SOLA does not merely output estimates. It outputs estimates together with the kernels that define what those estimates mean.

SOLA also gives a clear way to balance resolution against noise. The noise-aware objective \(\left\|\Tau-\mathbf XG\right\|_{\HS}^2 + \Tr(\mathbf X\mathbf C_D\mathbf X^*)\) contains two competing desires: \(\text{make resolving kernels look like target kernels,}\) and \(\text{avoid amplifying data noise too much.}\) This trade-off is not hidden. It can be inspected, tuned, plotted, and discussed.

SOLA is also property-focused. It does not demand that we reconstruct the whole model before asking for the quantity we care about. If the scientific question is already a linear property of the model, then SOLA tries to build that property directly from the data.

And, as Act 9 showed, SOLA has a clean frequentist role: it transforms the observation equation from data space to property space, pushing the noise law through \(\mathbf X\) and building calibrated confidence sets for the transformed quantities. This is the right framework for SOLA's uncertainty — not a shifted-noise cloud around the observation, but a frequentist procedure with repeated-sampling guarantees.

Intuition

SOLA is a data-to-property pipeline. Feed it an observation equation and a noise model, and it gives you the same equation in property space with calibrated confidence. The pipeline is good. The question is what you feed it.

What SOLA Cannot Do Alone

The caution is not that SOLA is weak. The caution is that SOLA is sometimes asked to carry more meaning than its construction supplies.

SOLA constructs \(\mathcal{A}:=\mathbf XG.\) The target property map is \(\Tau:\M\to\Pspace.\) The desired exact target property of the true model is \(\bar{\mathbf p} = \Tau(\bar m).\) The noiseless resolved property produced by SOLA is \(\mathcal{A}(\bar m).\)

These are the same only if \(\mathcal{A}=\Tau\) on the relevant model class. If not, then the difference is \(\Tau(\bar m)-\mathcal{A}(\bar m) = (\Tau-\mathcal{A})(\bar m).\) A small resolving-target mismatch is not, by itself, a model-independent guarantee that \(\mathcal{A}(\bar m)\approx\Tau(\bar m).\) To make that implication, we need some control of \(\bar m\).

Warning

SOLA can estimate resolved properties without a prior. It cannot turn resolved properties into exact target properties without some assumption about the model.

Similarly, the propagated covariance \(\mathbf C_P=\mathbf X\mathbf C_D\mathbf X^*\) is the covariance of a shifted-noise pushforward. As Act 9 argued, this measure is not a posterior on the model or on the target property. Without a prior, the observed data cannot be turned into posterior belief. The shifted-noise measure answers “what if we re-observed?” — and that is not the question the inverse problem asks.

The frequentist interpretation of Act 9 does not fix this by itself. It gives calibrated confidence sets — repeated-sampling guarantees for the transformed quantities — but confidence is not posterior probability. To turn a likelihood into a posterior, one needs a prior. That is not a limitation of SOLA. It is a structural fact about inference.

So SOLA alone should not be asked to provide:

  • exact target properties \(\Tau(\bar m)\) when \(\mathcal{A}\neq\Tau\), without model-side assumptions;
  • posterior uncertainty about \(\Tau(\bar m)\) without a prior or an equivalent model-side assumption;
  • useful uncertainty from the shifted-noise pushforward alone, since it is not connected to any model-space measure;
  • safe ratios or contrasts without checking the relevant resolving kernels together;
  • model-independent error bounds from kernel plots alone.

This is not a demotion. It is just bookkeeping. SOLA answers a precise question, and it answers it beautifully: \(\text{which resolved linear properties can I build from the available data?}\)

If we want a stronger answer — \(\text{what is the exact target property of the true model?}\) — then we need stronger assumptions.

Intuition

SOLA can tell us what the data can say after we choose a way of listening. It cannot tell us what the data never heard. And it cannot tell us what to believe without a prior to update.

The safest language is therefore: \(\widetilde{\mathbf p} \text{ estimates } \mathcal{A}(\bar m)\) with propagated data-noise covariance \(\mathbf C_P.\) If we also want to say that \(\mathcal{A}(\bar m)\approx\Tau(\bar m),\) then we should state what model-side assumptions make that approximation reliable. If we want posterior uncertainty, we should state a prior.

Ratios and Multi-Property Diagnostics

The same caution becomes sharper when SOLA outputs are combined after the fact.

Suppose we estimate two quantities, perhaps associated with two model components \(m_1,m_2\in\M,\) or with two different physical fields. Let \(\Tau_1:\M\to\mathbb R,\; \Tau_2:\M\to\mathbb R\) be the corresponding target property maps. Since their outputs are finite-dimensional, we write their one-dimensional property values as vectors: \(\mathbf p_1=\Tau_1(m_1)\in\mathbb R,\; \mathbf p_2=\Tau_2(m_2)\in\mathbb R.\) Their scalar components are \([\mathbf p_1]_1,\; [\mathbf p_2]_1.\)

SOLA does not generally return these exact target properties. It returns resolved quantities defined by approximate maps \(\mathcal{A}_1:=\mathbf X_1G_1,\; \mathcal{A}_2:=\mathbf X_2G_2.\) Thus the reported quantities are, in the noiseless idealization, \(\mathcal{A}_1(m_1),\; \mathcal{A}_2(m_2).\)

If we form a ratio of the SOLA outputs, we are forming something like \(\frac{[\mathcal{A}_1(m_1)]_1}{[\mathcal{A}_2(m_2)]_1}.\) But the intended target ratio may be \(\frac{[\Tau_1(m_1)]_1}{[\Tau_2(m_2)]_1}.\) In general, \(\frac{[\mathcal{A}_1(m_1)]_1}{[\mathcal{A}_2(m_2)]_1} \neq \frac{[\Tau_1(m_1)]_1}{[\Tau_2(m_2)]_1}.\)

The issue is not only that each resolving kernel might differ from its target. The issue is that the two resolving kernels may differ from each other in ways that matter to the ratio.

For example, suppose the two target kernels are meant to localize the two quantities in the same region. If the resolving kernel for the numerator is narrow, but the resolving kernel for the denominator is broad, then the ratio is mixing two different spatial averages. If one resolving kernel has side lobes and the other does not, the ratio inherits that asymmetry.

Warning

A ratio of SOLA outputs is a ratio of resolved quantities. It is not automatically the ratio of the corresponding target quantities.

This does not mean ratios are forbidden. It means they require matched interpretation.

A safer ratio statement would be: \(\frac{[\mathcal{A}_1(m_1)]_1}{[\mathcal{A}_2(m_2)]_1}\) is the ratio of two resolved quantities, where the numerator is resolved through \(\mathcal{A}_1\) and the denominator is resolved through \(\mathcal{A}_2\). If \(\mathcal{A}_1\) and \(\mathcal{A}_2\) have sufficiently compatible resolving kernels for the intended scientific question, then the ratio may be meaningful.

But there is a deeper frustration here. Each SOLA output comes with its own resolving kernel, so each value must be interpreted through its own custom lens. If you want uniform interpretation — the ability to compare, combine, or ratio outputs without individually auditing every kernel — the only way to get that is by introducing prior information. With a sufficiently informative prior, one can place bounds on the actual desired target properties, and then it is simply a matter of using the same target kernels wherever needed.

Without a prior, you might be tempted to say: “My resolving kernels are very close to the targets. Surely the approximate property cannot be that far from the desired one.” But as we saw in Act 7, it can be arbitrarily far off, no matter how close the resolving kernels are to the targets. Then you might say: “Sure, it could be far off if the true model is very weird, but surely it is not in my case.” But that — the belief that the true model is not weird — is prior information. If you have it, be honest and rigorous: put it in the problem.

The Final Slogan

We can now compress the whole story: \[\boxed{\text{SOLA transforms the observation problem into a more useful form.}}\]

The first half — transforms the observation problem — is the constructive heart of SOLA. The method takes a data-space observation equation and transports it to property space. It builds resolving kernels that make the transport visible. It lets the practitioner design the target question and inspect what the data can actually deliver. That is genuinely useful.

If we want more — posterior beliefs, exact target properties, useful uncertainty about \(\Tau(\bar m)\) — we need to add something from the model side. That something may be deterministic: \(\bar m\in B\subset\M.\) It may be probabilistic: \(m\sim\muprior.\) It may come from physics, geology, smoothness, boundedness, or earlier experiments. But it should be stated, not smuggled in.

So my take on SOLA is not that it should be discarded. Far from it. SOLA is a neat and useful method precisely because it focuses on properties, exposes resolving kernels, makes the resolution-noise trade-off visible, and transforms the observation problem cleanly.

But its outputs should be read with the right grammar.

A SOLA number is not just a number. It comes with a kernel.

A SOLA error bar is not posterior uncertainty. It is propagated data-noise — a summary of a shifted-noise pushforward, not a statement about the true property.

A target kernel is not a promise. It is a design request.

And if we want to turn resolved measurements into exact claims about the true model, we must say what we believe about the model.

Checkpoint

The mature use of SOLA is neither blind trust nor rejection. It is careful labelling: resolved quantity, resolving kernel, frequentist confidence, and explicit model assumptions when exact target properties or posterior beliefs are claimed.
