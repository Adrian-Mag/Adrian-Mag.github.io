The CPU and the Computer

Movement II · The harness

1 Box 2 Kernel 3 Chat box 4 CPU 5 Anatomy 6 AGENTS.md 7 Skills 8 Hooks 9 Tools 10 Context 11 Orchestration S Summary
Act 4 Current as of July 2026

A processor is a remarkable object that can do nothing on its own. It cannot store anything for later, reach a disk, notice the passage of time, or produce a single visible effect in the world. It computes, and it waits to be asked. Everything else you think of as “the computer” is the machinery built around that fact.

The comparison is not mine, and whose it is matters. Andrej Karpathy popularised the framing of a language model as “not a chatbot, but the kernel process of a new Operating System”.1 I want to narrow it, because the narrower version is more useful: the model is the processor, and the harness is the rest of the computer. Locating it that way makes the interesting question obvious. It is not “how fast is the chip?” but “what has been wired to it?”

He drew it, which saves a great deal of description.

diagram · Andrej Karpathy, X, 11 November 2023

Architecture, not product specificationsThis is a local relationship diagram, not a measurement of any model’s speed, context window, or product features. The durable point is structural: a language model becomes useful only when surrounding software supplies context, I/O, and checks.

My one quarrel with the picture is the CPU box itself, and it is the reason for the narrowing. Drawing the LLM as the CPU invites you to read the diagram as a portrait of the model. It is not. It is a portrait of everything the model is missing. Line up what Act 2 established against what a processor lacks and the correspondence is almost embarrassing.

Somewhere to hold what it is working onThe context window: small, fast, wiped between runs
Storage that outlives the runFiles, databases, memory directories

A clockThe harness, which knows what time it is

None of that is in the model. All of it is in the machinery around it, and every item is something a person wrote and can change.

The mechanism: it asks, it never acts

Here is the part that surprises people who have watched one of these systems edit a file. I will state it as flatly as I can.

The model cannot run anything. When it “runs a command”, what actually happens is that it emits text in a structured form: a request naming a tool and its arguments. That request goes to the harness. The harness decides whether to honour it, executes it, captures the output, and appends that output to the conversation. Then the whole enlarged conversation goes back to the model, which reads the result and decides what to ask for next.

Predict, request, execute, append, repeat. That loop is the whole of what the word agent denotes. Anthropic’s working definition is worth borrowing because it is unusually plain: agents are “systems where LLMs dynamically direct their own processes and tool usage, maintaining control over how they accomplish tasks”, as against workflows, where those steps are “orchestrated through predefined code paths”.3 The distinction is about who chooses the next step, not about how clever the system is.

The interleaving of reasoning and acting (think a little, do a little, look at what came back, think again) was studied under the name ReAct well before any of this reached products.4 Nearly every coding agent you can use today is a descendant of that shape.

The three-step trace is the entire mechanism with nothing else in the way. The model wanted to know the working directory. It could not look. It asked, something else looked, and the answer arrived as text it then read back.

The longer trace is the same mechanism doing something that feels much more capable. Notice how expensive that feeling is. To look at a web page (something you do in a fraction of a second, continuously, without noticing) the model must ask for a scroll, then ask for a screenshot, then ask to read the resulting image file. Three round trips, repeated for each screenful. It is not seeing the page. It is requesting narrow slices of evidence about the page and assembling a belief from them.

Hold onto that, because it generalises. Everything these systems appear to do decomposes into asking for evidence and asking for effects. The apparent capability is a property of what they are permitted to ask for, which is to say a property of the harness.

Why this makes the harness the interesting object

Once the loop is visible, a lot of otherwise-confusing things become ordinary engineering questions.

Why can one assistant edit your files while another cannot? Because someone gave the first a file-editing tool. Why does one stop and ask before deleting something? Because the harness classified that request as needing confirmation. Why does one seem to know your project’s conventions? Because something put them in the context before the model ever saw the question. Why does one degrade badly on a long task? Because the loop keeps appending, the context window is finite, and something has to decide what to drop.

None of those are questions about intelligence. They are questions about wiring. Every one of them has an answer you can inspect, and usually change.

Which raises the obvious next question: what is actually in one of these things?
