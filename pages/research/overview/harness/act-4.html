The CPU and the Computer

Movement II · The harness

Act 4 Current as of — (set at publication)

A processor is a remarkable object that can do nothing on its own. It cannot store anything for later, reach a disk, notice the passage of time, or produce a single visible effect in the world. It computes, and it waits to be asked. Everything else you think of as “the computer” is the machinery built around that fact.

The comparison is not mine, and it is worth being precise about whose it is. Andrej Karpathy popularised the framing of a language model as “not a chatbot, but the kernel process of a new Operating System”.1 What I want to do here is narrow it, because the narrower version is more useful: the model is the processor, and the harness is the rest of the computer. Locating it that way makes the interesting question obvious — not “how fast is the chip?” but “what has been wired to it?”

Line up what Act 2 established against what a processor lacks and the correspondence is almost embarrassing.

The machine needsSupplied by
Somewhere to hold what it is working onThe context window — small, fast, wiped between runs
Storage that outlives the runFiles, databases, memory directories
Input and outputTools — the only way anything reaches the world
A clockThe harness, which knows what time it is
Something to decide what runs, and whether it mayThe agent loop and its permission system

None of that is in the model. All of it is in the machinery around it, and every item is something a person wrote and can change.

The mechanism: it asks, it never acts

Here is the part that surprises people who have watched one of these systems edit a file, and it is worth stating as flatly as possible.

The model cannot run anything. When it “runs a command”, what actually happens is that it emits text in a structured form — a request naming a tool and its arguments. That request goes to the harness. The harness decides whether to honour it, executes it, captures the output, and appends that output to the conversation. Then the whole enlarged conversation goes back to the model, which reads the result and decides what to ask for next.

Predict, request, execute, append, repeat. That loop is the whole of what the word agent denotes. Anthropic’s working definition is worth borrowing because it is unusually plain: agents are “systems where LLMs dynamically direct their own processes and tool usage, maintaining control over how they accomplish tasks”, as against workflows, where those steps are “orchestrated through predefined code paths”.2 The distinction is about who chooses the next step, not about how clever the system is.

The interleaving of reasoning and acting — think a little, do a little, look at what came back, think again — was studied under the name ReAct well before any of this reached products.3 Nearly every coding agent you can use today is a descendant of that shape.

The three-step trace is the entire mechanism with nothing else in the way. The model wanted to know the working directory. It could not look. It asked, something else looked, and the answer arrived as text it then read back.

The longer trace is the same mechanism doing something that feels much more capable, and it is worth noticing how expensive that feeling is. To look at a web page — something you do in a fraction of a second, continuously, without noticing — the model must ask for a scroll, then ask for a screenshot, then ask to read the resulting image file. Three round trips, repeated for each screenful. It is not seeing the page. It is requesting narrow slices of evidence about the page and assembling a belief from them.

That is worth holding onto, because it generalises. Everything these systems appear to do decomposes into asking for evidence and asking for effects. The apparent capability is a property of what they are permitted to ask for — which is to say, a property of the harness.

Why this makes the harness the interesting object

Once the loop is visible, a lot of otherwise-confusing things become ordinary engineering questions.

Why can one assistant edit your files while another cannot? Because someone gave the first a file-editing tool. Why does one stop and ask before deleting something? Because the harness classified that request as needing confirmation. Why does one seem to know your project’s conventions? Because something put them in the context before the model ever saw the question. Why does one degrade badly on a long task? Because the loop keeps appending, the context window is finite, and something has to decide what to drop.

None of those are questions about intelligence. They are questions about wiring — and every one of them has an answer you can inspect, and usually change.

Which raises the obvious next question: what is actually in one of these things?
