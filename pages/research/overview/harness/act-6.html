Act 6 Current as of July 2026

The cheapest lever: a file the harness reads and injects into context. Not enforced: guidance, not law. Why that is both its weakness and its strength.

Here is the first thing I changed when I wanted an agent to stop treating every repository as the same repository. I added a text file.

The file is called AGENTS.md. It is not a model, a plug-in, or a program. It is ordinary Markdown containing the facts and working agreements that would otherwise have to be repeated at the start of every conversation: where the real source lives, how to run the tests, what must never leave the machine, and what “finished” means here.

A supporting harness finds the file and places its contents in the context it assembles for the model. That is the whole mechanism. Nothing is trained, and no weight inside the model changes. The machine from Acts 4 and 5 simply adds one more piece of text before asking the model what to do.

What enters the context? Mechanism diagram
Harness You are a coding agent working in this repository.
AGENTS.md After editing a notes page, rebuild media/search-index.json.
User Draft the next act of the series.

The project rule is present as input to the model. The harness has not turned it into executable code.

Use the button. With the file absent, the model receives the same task but loses the repository-specific fact. It might discover the search-index command by exploring. It might not. With the file present, the work begins with that fact already available.

The file for this website

The example below is not an idealised template. It is a verbatim snapshot of this website’s own AGENTS.md, screened for credentials, addresses, hostnames, and private material on 24 July 2026. Open it and read it as a working document. It is deliberately mundane.

The useful parts answer some combination of five questions:

QuestionWhat the file supplies
Where am I?The purpose of the repository and the files that actually matter
How is work done?Commands, environments, paths, and established workflows
What is forbidden?Privacy boundaries, dangerous operations, and integrity rules
Where should I look first?Living references, source inventories, and routing instructions
How do I know I am finished?Builds, tests, regenerated assets, and other verification steps

This is why a useful file looks more like an operations note than a personality prompt. “Be careful” does not identify a risk. “After editing any notes page, run python3 tools/build_search_index.py” identifies an action, its trigger, and the artifact that should change. One can be checked. The other can only be admired.

Which file applies?

The filename is a convention interpreted by the harness, so the precise discovery rules are product features rather than properties of language models. They have to be dated.

Codex behaviour, checked 24 July 2026 Codex reads an instruction chain once at the start of a run. It first checks the user’s Codex home, then walks from the project root down to the working directory. A file closer to the work appears later in the combined instructions and overrides broader guidance where they conflict. Empty files are skipped; the default combined project-instruction limit is 32 KiB. Other harnesses may discover or order instruction files differently.1

That nesting is more important than it first sounds. A repository can say “run the test suite before stopping” at its root, while a directory containing slow numerical experiments can give the exact command and resource limits that apply only there. The reader gets a route from general to specific instead of one enormous manual for every possible task.

Guidance is not enforcement

The file in the panel is text. The harness may give it a privileged place in context, but no separate process watches the model and forces the search index to be rebuilt. The instruction can be ambiguous. It can conflict with something more specific. It can be truncated from an overgrown instruction chain. The model can simply make a mistake.

This is the weakness of AGENTS.md: it changes the evidence and instructions available to a probabilistic system, not the laws of the computer around it. Writing “never stage the private control overlay” is useful, but it does not alter the Git index. Writing “run the tests” does not make a failing test prevent a commit.

It is also the strength. The file costs almost nothing to create, can be reviewed in the same pull request as the code, travels with the repository, and changes on the next run. You do not need to build a tool or retrain a model to teach the harness that this website has no build step.

The right division is simple: use text to state intent, context, and working practice. Use settings, permissions, hooks, tests, and sandboxes for properties that must hold even when the model is confused. Official Codex guidance makes the same separation, recommending that project guidance be paired with enforcing infrastructure such as hooks, linters, and type checkers.1 Act 8 will make that boundary concrete.

Write the scar tissue

The best rule usually begins with a mistake that actually happened. An agent edited a notes page and left the search index stale. The next sentence in AGENTS.md says exactly when and how to rebuild it. A command was run from the wrong directory, so the file records the correct working directory. A reviewer had to ask twice for source-grounded claims. The instruction becomes durable on the second occurrence.

Start with those scars. Keep the file short enough to be read, concrete enough to be followed, and close enough to the relevant work to stay true. If a rule needs a page of explanation, point to that page. If it needs expertise, examples, scripts, and references that should load only for one kind of task, a flat instruction file has reached its limit.

That larger package has a name. It is the subject of the next act.
