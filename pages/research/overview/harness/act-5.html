Anatomy of a Coding Agent

Movement II · The harness

1 Box 2 Kernel 3 Chat box 4 CPU 5 Anatomy 6 AGENTS.md 7 Skills 8 Hooks 9 Tools 10 Context 11 Orchestration S Summary
Act 5 Current as of July 2026

The same model sits behind the chat box and behind the tool that refactors a codebase overnight. If the processor is identical, the difference has to be somewhere else. It is, and it is not hidden — it is a list of components, each of which someone decided to build.

This act is an inventory. It is the least conceptual part of the series, and possibly the most useful, because once you can name the components you can ask which ones you have.

Tools: the entire surface between the model and the world

Everything a model can affect, it affects through a tool. There is no other channel. A coding harness typically exposes something like: read a file, write a file, edit part of a file, list files matching a pattern, search file contents, run a shell command, fetch a URL, search the web.

That list looks mundane, and its mundanity is the point. There is no “understand the codebase” tool. What looks like understanding is a great many small requests — search for this, read that, look at the file the first search pointed to — assembled in the loop from Act 4. The capability is emergent from a boring inventory plus a lot of round trips.

Notice also what granularity buys. A harness that offers only “run a shell command” can technically do everything, since editing a file is a shell command. But then every action arrives as an opaque string, and the harness cannot tell a harmless search from a destructive delete. Promoting an action to its own tool — with named arguments — is what makes it possible to gate it, display it properly, log it, or run several in parallel. That trade-off is Act 9.

Permissions: which requests are honoured

The harness sits between the request and the execution, so it can refuse. Typically: some tools run freely, some require confirmation, some are forbidden outright, and the rules can vary by directory or by argument.

This is the first component that is a genuine safety mechanism rather than a capability, and it has a property worth pausing on: it does not depend on the model’s cooperation. A model that has been talked into something by a malicious web page still only emits a request, and that request still hits the same gate. Act 8 is about what follows from that — and about how much less it guarantees than it first appears.

Context management: deciding what the model is allowed to know

The loop appends. Every request and every result joins the transcript, and the transcript is re-sent every turn. On a long task it will outgrow the context window — not might, will.

So something must decide what to drop: summarise the middle, discard old tool output, keep the current file and forget the one from an hour ago. Those decisions are invisible, unglamorous, and they largely determine whether a long session stays coherent. Act 10 is entirely about this.

Subagents: buying a second context window

A harness can start a second loop with its own fresh context, hand it a narrow task, and receive only the answer. The expensive intermediate reading never enters the main transcript.

Read that again as a resource-management move rather than a clever trick, because that is what it is: the scarce resource is context, and a subagent is how you spend someone else’s.

Persistence: what survives the session

Files on disk, notes the model was told to keep, a project instruction file read at startup. The model has no memory; a harness can give it a filing cabinet. Acts 6 and 10 cover the two ends of this.

The comparison

Same processor. Different machine.

ComponentConsumer chat boxCoding harness
ToolsFew, generic — often web search and a sandboxed interpreterA dozen or more, aimed at a filesystem and a shell
Reaches your machineNoYes — that is the entire point
PermissionsFixed by the vendorConfigurable by you, per tool and per project
Context managementAutomatic, opaqueConfigurable, inspectable, often noisy about it
SubagentsNoCommonly
PersistenceVendor-managed memory, if anyFiles, instruction files, notes you can read and edit
You can changeYour wordingNearly all of the above

The last row is the one that matters, and it is the hinge of this series. In a chat box, the only variable under your control is how you phrase things — which is why prompt-wording advice became a genre. In a harness, the wording is one small input among many, and it is usually not the one that is limiting you.

An honest caveat

Bigger is not better by default. Every component above is a place to misconfigure something: a tool nobody needed, a permission rule that fires on the wrong thing (Act 8 has a real example of exactly that), a context strategy that discards the thing you were about to need, a subagent dispatched for work that would have taken one search.

A large harness is not a more powerful assistant. It is a more powerful instrument — which is a different claim, and it includes the possibility of using it badly.

The rest of this series takes the components one at a time, cheapest first. The next one costs nothing: a text file the harness reads before it does anything else.
