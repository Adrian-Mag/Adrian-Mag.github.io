Tool design. Definitions as interface contracts; why descriptions are load-bearing. The promote-to-a-dedicated-tool heuristic: gate, render, audit, parallelize. Closes with a short MCP section: host, client, server, and the one real invocation on record.

A model can ask for a capability only if the harness tells it that the capability exists. Usually that introduction is a compact definition: a name, a description, and a schema for the arguments. The implementation remains outside the model. What enters context is the interface.

That makes a tool definition more than API paperwork. It is a contract between three parties. The model sees what it may request. The harness learns how to validate and route the request. The implementation promises what it will return. If the contract is vague, all three can disagree while every component is behaving exactly as specified.

A real tool for this website

The tool below was built inside this public repository for this act. inspect_site_page accepts one repository-relative HTML path and returns a page title, meta description, heading outline, and local CSS and JavaScript dependencies. It cannot edit a file, return the page's body prose, inspect another file type, or follow a path outside the repository.

A distinct, action-shaped identity gives the model and router an unambiguous handle.

model request→schema validation→handler→structured result

The middle button contains the exact 50-word description in the public definition. It states the job, the circumstances in which it is useful, and four things it must not be used for. That text is load-bearing because it is part of what the model receives when deciding whether the capability fits a request. Current OpenAI function-calling guidance likewise defines a description as explaining when and how to use a function, and recommends stating purpose, output shape, and when not to use it.1

The schema carries a different kind of meaning. It says that page is required, that extra properties are not accepted, and that the input must look like a relative .html path. The handler then performs the security-relevant check that a regular expression cannot: it resolves the path and verifies that the result still lies under the repository root.

When a command deserves a dedicated tool

A general shell is an excellent starting point. It already knows how to combine small programs, so there is little value in wrapping every command. Promotion becomes useful when repetition reveals a boundary that deserves a name. Four pressures are especially practical:

GateConstrain paths, fields, actions, or permissions before implementation code runs.
RenderTurn a messy source into the small structured result the next step actually needs.
AuditGive repeated work a stable request and response shape that can be logged and tested.
ParallelizeSplit independent units into separate calls that a harness can schedule concurrently.

This exhibit earns promotion on the first three grounds. The path check gates access. The parser renders HTML as a compact outline. The schema and recorder make calls auditable. A harness could issue independent page inspections concurrently, but this single handler does not itself run work in parallel.

A dedicated tool is not automatically safer. Its description can be misleading, its schema can admit dangerous inputs, and its implementation can ignore both. Even the read-only and idempotent annotations in this contract are hints. The stable MCP specification tells clients not to trust tool annotations unless the server itself is trusted.2 Enforcement still belongs in code and in the harness boundary around it.

MCP: a standard connection, not another model

Tool definitions solve the local interface problem. The Model Context Protocol standardizes how an application connects to external providers of tools and context. In the stable 2025-11-25 architecture, a host is the LLM application coordinating the experience and security boundaries. A client inside that host maintains an isolated connection to one server. The server exposes a focused set of capabilities.3

Nothing in this sequence changes the model. A tool definition makes a capability legible. A handler makes it real. A harness validates, executes, and returns the result. MCP gives hosts and capability providers a shared way to connect those pieces. The new sense belongs to the machine around the model.
